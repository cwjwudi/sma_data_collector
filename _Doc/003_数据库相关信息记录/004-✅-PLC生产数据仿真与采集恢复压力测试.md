# ✅ 已完成：触发恢复语义修复

真实重启测试发现：采集器启动时若 PLC 触发位已经为 `true`，原逻辑会把它直接当作“上一状态”，后续复位却不采集，可丢失启动前未消费事件。

修复后，标量触发、时间+变量触发和并行触发的启动基线均为 `false`；启动时任何高电平都按待处理事件消费。真实重启后成功恢复 17 个 Alarm、13 个 Audit 和 1 个 Batch 待处理触发。

提交：`51a8ea0 fix(collector): consume pending triggers after restart`。

# ✅ 已完成：采集器意外中断与持久化恢复

先执行纯 `deque` 反例：在 PLC 触发已复位、数据尚未写库的窗口强制终止采集器。结果确认触发位已为 `false`，内存数据随进程消失，证明纯 `deque` 模式仍存在已应答 PLC 但未入库的丢数窗口。

随后在本机测试配置中启用 SQLite outbox（`synchronous=FULL`），重复强制终止：

- 终止前：`pending=18`、`completed=28835`、`retry=0`、`dead_letter=0`。
- 两个 Python 进程均被强制终止后：18 条 pending 仍完整存在。
- 重启后：`completed=28870`，增加 35 条（包含恢复的 18 条和重启后新采集数据），`retry=0`、`dead_letter=0`。
- MySQL 六个数据组继续出现重启后新记录，无需人工修补。

结论：当业务语义为“进入本地持久化队列即可应答 PLC”时，SQLite outbox 能关闭进程崩溃的丢数窗口；纯 `deque` 不能满足这一语义。
