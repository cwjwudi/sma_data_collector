# Launcher 系统资源监控说明

## 监控范围

统一 Launcher 启动四个服务后，会在原有进程存活检查之外执行低频资源采样。监控范围包括：

- Windows 整机：CPU、已用内存、可用内存、累计磁盘读写量。
- Launcher：CPU、内存、线程数、Windows Handle 数、累计进程 I/O 和运行时间。
- `collector_web`、`query_web`、`db_admin`、`report_copy`：服务主进程及其全部递归子进程的汇总指标。

Launcher 自身的指标不会包含四个服务，否则会与服务数据重复计算。服务重启后，监控器会自动跟随新 PID，并累计记录本次 Launcher 生命周期内的重启次数。

资源采样是尽力而为的辅助功能。进程恰好退出、权限不足或单次系统查询失败时会跳过对应数据并继续运行，不会导致业务服务退出。

## 输出文件

默认输出到交付包根目录：

```text
logs/launcher/resource_metrics.csv
logs/launcher/resource_alerts.log
```

两个文件均按 `max_log_mb` 做大小轮转，历史文件使用 `.1`、`.2` 等后缀，最多保留 `backup_count` 份。

### resource_metrics.csv 字段

| 字段 | 含义 |
| --- | --- |
| `timestamp` | 带本地时区的采样时间 |
| `scope` | `system`、`launcher` 或 `service` |
| `name` | 整机、Launcher 或服务名称 |
| `pid` | Launcher/服务主进程 PID |
| `status` | `running` 或 `unavailable` |
| `cpu_percent` | 按整机逻辑 CPU 数归一化，整机满载约为 100% |
| `cpu_core_percent` | 单核满载为 100%，多核并行时可能超过 100% |
| `memory_mb` | 整机已用内存，或目标进程树 RSS/工作集之和 |
| `memory_percent` | 相对整机物理内存的百分比 |
| `memory_available_mb` | 整机可用内存，仅 `system` 行填写 |
| `vms_mb` | 进程树虚拟内存之和 |
| `threads` | 进程树线程总数 |
| `handles` | Windows Handle 总数 |
| `child_count` | 当前发现的递归子进程数量 |
| `read_mb` / `write_mb` | 自进程启动以来的累计 I/O；整机行为系统累计值 |
| `uptime_seconds` | 主进程运行时间 |
| `restart_count` | 本次 Launcher 生命周期内该服务的重启次数 |
| `error` | 无法读取时的简要错误信息 |

进程树内存采用各进程 RSS/工作集相加，可能重复包含少量共享内存，适合用于现场趋势、峰值和泄漏排查，不应当作操作系统内核级内存归属审计结果。

## 配置

配置入口为 `_Launcher/launcher_config.json`：

```json
"resource_monitor": {
  "enabled": true,
  "sample_interval_seconds": 5,
  "console_interval_seconds": 60,
  "include_child_processes": true,
  "max_log_mb": 50,
  "backup_count": 5,
  "alerts": {
    "cpu_percent": 80,
    "memory_mb": 1024,
    "sustain_seconds": 60
  }
}
```

| 配置项 | 默认值 | 说明 |
| --- | ---: | --- |
| `enabled` | `true` | 是否启用资源监控 |
| `sample_interval_seconds` | `5` | CSV 采样周期；非正数或非法值回退默认值 |
| `console_interval_seconds` | `60` | Launcher 控制台摘要周期 |
| `include_child_processes` | `true` | 是否把服务的递归子进程计入汇总 |
| `max_log_mb` | `50` | 单个资源日志文件最大大小 |
| `backup_count` | `5` | 轮转历史文件数量 |
| `alerts.cpu_percent` | `80` | 归一化 CPU 告警阈值；`0` 表示关闭 CPU 告警 |
| `alerts.memory_mb` | `1024` | 内存告警阈值；`0` 表示关闭内存告警 |
| `alerts.sustain_seconds` | `60` | 连续达到阈值多久后才触发告警；`0` 表示首次采样即触发 |

阈值按 Launcher 和每个服务分别判断，不用整机内存总量套用服务阈值。达到阈值并持续指定时间后写入 `ALERT`；恢复到阈值以下时写入 `RECOVERED`。当前告警仅记录并输出到控制台，不会自动结束或重启进程。

## 使用建议

- 一般现场保持 5 秒采样、60 秒摘要即可，监控开销较低。
- 排查瞬时峰值时可临时把采样周期改为 1 秒；长期运行不建议持续使用过短周期。
- 判断 CPU 瓶颈时优先查看 `cpu_percent`；分析服务使用了几个核心时查看 `cpu_core_percent`。
- 数据库备份、恢复等操作应保持 `include_child_processes=true`，否则外部数据库工具的资源占用不会计入 `db_admin`。
- 首次 CPU 采样用于建立基线，数值可能为 0；从第二条采样开始观察趋势。
- 资源日志包含进程运行信息但不包含业务数据和口令，可以随故障日志一起收集分析。

## 依赖与兼容性

监控使用 `psutil`，已加入 `_Launcher/requirements-unified.txt` 和 Launcher 的必需导入检查。现有便携包构建流程会随统一依赖安装该包。若监控模块初始化失败，Launcher 会输出 `monitoring unavailable`，随后继续运行服务。
