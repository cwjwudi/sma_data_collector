## 已完成的专项结果

1. 动态间隔：20 秒内记录 12 个事件，其中定时记录稳定在约 2 秒间隔，
   `dynamic_interval_changed=1`。
2. 外部启停：Product 关闭窗口事件数为 0；关闭前缓存 3 行全部提交，
   恢复后继续采集。
3. 点位覆盖：Product 共 10 条记录，其中 3 条变量触发记录全部使用覆盖点位
   值，未发现异常值。
4. 快速重连：45 秒内主动断线 2 次，恢复耗时分别为 0.110 秒和
   0.109 秒；前后订阅句柄数均为 3；提交 236 行，无死信。
5. 持久队列故障：数据库写入故障期间观察到 13 条 retry；恢复后累计提交
   21 行，pending/processing/retry/dead-letter 全部归零。
6. 自动化回归：`212 passed`，另有 4 个既有测试告警；Python compileall
   及两个前端 JavaScript 文件语法检查通过。
7. 依赖兼容：asyncua 2.0.0 不支持 `auto_reconnect` 构造参数，客户端现按
   API 能力传参；asyncua 2.0.0 与 2.0.1 环境的重连测试均为 11 passed。
8. 日志轮转：首轮断线后目录中保留 5 个轮转文件和 1 个当前日志文件，
   符合 `backup_count=5`。

## 一小时混合模式长稳

长稳测试从干净的专用数据库和持久队列启动，要求六组均持续产生事件，并在
第 10、30、50 分钟主动断开两个 OPC UA 会话。通过条件为：运行不少于
3600 秒、三次故障全部恢复、最终双连接为 connected、六组数据库增量均大于
0、队列完全清空、无死信且脚本无错误。

最终结果：通过。

- 实际时长：3,605.485 秒。
- 采集事件：Recipe 114、Product 1,850、Alarm 535、Audit 385、
  Batch 76、BatchInfo 265。
- 触发类型：Product 定时 1,803、变量 47；其他五组均产生变量触发。
- 故障注入：第 600、1,800、3,000 秒分别断开两个连接，共 6 次；全部恢复，
  单次恢复耗时 0.109–0.125 秒。
- 订阅恢复：主连接句柄数每次为 2 → 2，次连接为 1 → 1。
- 数据库：累计提交 3,225 行，失败 0；六组最终增量均大于 0。
- 持久队列：pending/processing/retry/dead-letter 均为 0，停机残留 0。
- 最终连接：`PLC_TPS=connected`、`PLC_TPS_SECONDARY=connected`。

原始计数中 Recipe 的 `rows_before=null` 表示启动时年度分区表尚不存在，
并非读取失败；启动后自动建表并在结束前读到 111 行。因此增量规则将
“运行前不存在的分区表”按 0 行基线处理，Recipe 增量为 111。完整机器可读
证据见 `test_results/aa_full_function/mixed_mode_soak_1h.json`。

## 过程发现

- PLC 数组触发可能在采集器启动前已经处于待处理状态。若分区数据组在首个
  Batch 上下文建立前消费这些触发，会因缺少批次上下文进入重试/死信。测试
  配置将 Alarm/Audit 固定表化，Recipe 单独承担分区验证，避免把两个独立
  功能不必要地耦合。
- 相对持久队列路径按进程工作目录解析。实机测试必须从
  `SD_SMA_DATA_COLLECTOR` 目录启动，以确保运行文件保持在用户限定范围内。
- asyncua 2.0.0 与 2.0.1 的 `Client` 构造参数不同；兼容处理可避免旧环境
  在连接前直接进入重复重连告警。
