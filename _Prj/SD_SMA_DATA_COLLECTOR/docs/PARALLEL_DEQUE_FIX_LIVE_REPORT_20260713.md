# 并行触发 deque 修复实机回归报告

## 范围

- 分支：`fix/collector-parallel-deque`
- PLC：`192.168.50.233`
- 配置：`config/collector/AA_SMA_DATA_TEST.json`
- 数据库：配置指定的 MySQL 测试库
- 未构建或下载 PLC 程序。

## 修复前基线

61 分钟压力测试中，快速重触发在 `Data_Alarm` 和 `Data_Audit` 共复现 2398/2398 次卡高漏采。正常停机时 `Data_Alarm` 未满批次的 90 行被清空但未写入数据库。

## 第一轮修复回归及发现

第一轮 3 分钟回归完成 55 轮。正常触发均成功，数据库与回调各增加 550 行，但读回确认与测试端快速重置之间仍存在竞态：采集器可能把复位后立即出现的新 True 误判为复位失败并再次清零。

据此调整为：数组写 False 成功后，如果读回已为 True，则认为 PLC 可能已经产生新事件；不进行第二次清零，并把内部前态保持为 False，让下一轮消费该高电平。

## 第二轮修复回归

- 持续时间：122.494 秒
- 循环：37
- 每轮对两个并行组分别执行正常触发和复位窗口内快速重触发。
- 每次使用 10 个数组索引。

| 指标 | Data_Alarm | Data_Audit |
| --- | ---: | ---: |
| 正常触发成功 | 37 | 37 |
| 快速重触发成功复位 | 37 | 37 |
| 快速重触发卡 True | 0 | 0 |
| 采集回调行数 | 740 | 740 |
| MySQL 行数增量 | 740 | 740 |
| 正常停机剩余队列 | 0 | 0 |

最终满足：

```text
两个组的回调行数 = 两个组的数据库增量 = 1480
快速重触发卡高 = 0
停机剩余队列 = 0
```

## 剩余边界

当前使用内存 deque。正常运行、数据库瞬时失败和正常停机已具备重试/刷新保护，但断电、操作系统崩溃或进程被强制终止仍可能丢失尚未提交 MySQL 的内存数据。该风险留给后续 SQLite/持久化 outbox 特性处理。
