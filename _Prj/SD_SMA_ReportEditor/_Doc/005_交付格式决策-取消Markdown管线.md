# 交付格式决策：取消独立 Markdown 生成与归档

> **状态：** 已采纳（2026-05）  
> **关联：** [002_里程碑与工单.md](002_里程碑与工单.md) M6、[001_项目计划.md](001_项目计划.md)（初版仍描述 Markdown，以本文为准）

---

## 结论

**当前产品不再需要将报表保存为 `.md` 文件，也不再实现后端的 `generator_module` / `history_module`（`data/history/*.md`）管线。**

现场交付与日常使用的唯一正式产出物是 **PDF**：

- **生成报表**：`ReportGenerator.vue` — 手动或 OPC 条件触发，经 Electron 渲染栈导出 PDF  
- **历史报表**：`ReportHistory.vue` — 监视用户指定的**导出文件夹**中的 PDF（与自动导出目录可共用）  
- **模版与版式**：仍以 **JSON** 保存在 `backend/data/templates/`、`layout_presets` 等，与「报表成品格式」无关  

编辑器内的「预览」是 **所见即所得的布局预览**（与 PDF 导出同一套栈），不是「先拼 Markdown 再转 PDF」的两段式流程。

---

## 取消理由（为何不再做 Markdown 成品）

### 1. 业务交付形态是「可打印 / 可归档的版式文档」

药机现场与质量归档通常要求 **固定版式**（页眉页脚、表格线、签名区、分页），而不是可二次编辑的 Markdown 文本。PDF 能锁定版式；Markdown 在不同渲染器下版式不一致，还需额外转 PDF 才能满足打印与签章场景。

### 2. 技术实现已转向「版式 + 区带」模型，与 Markdown 拼接不匹配

初版设想是六种元素拼成 Markdown 字符串（标题、表格转 `| col |` 等）。实际产品演进为：

- 版式预设（纸张、页眉页脚区带）  
- 模版内控件缩放、表格 SQL 填充、签名图  
- `TemplateExportPreviewStack` 与 PDF 导出共用同一渲染路径  

若再维护一套「元素 → Markdown」生成器，等于 **双轨实现**（一套给预览字符串、一套给 PDF），成本高且易出现预览与成品不一致。

### 3. 历史留存方式更简单、更符合桌面软件习惯

原设计：每次生成写入 `backend/data/history/report-xxx.md` + `.meta.json`，由后端 API 列表。

现设计：PDF 写入用户可选的文件夹（含自动导出目录），`ReportHistory` 直接列举该目录。优点：

- 用户可用现有网盘 / NAS / 备份策略管理 PDF  
- 不膨胀 `backend/data`  
- 与 Windows / macOS 安装版「用户数据在 AppData / Application Support」的职责划分更清晰（配置在应用数据目录，**报表成品在用户选的导出目录**）

### 4. 命名与仓库标题中的「Markdown」

仓库名 **SD_SMA_ReportEditor**、早期文案中的「Markdown 报表」反映的是 **立项阶段** 的技术选型设想，不是当前交付承诺。对外说明应以 **「报表模版 + PDF 导出」** 为准。

---

## 仍保留的与「文本」相关的能力（不是成品 Markdown）

| 能力 | 说明 |
|------|------|
| 模版 JSON | 结构、绑定、版式引用，持久化在 `data/templates/` |
| SQL / OPC 绑定 | 导出时由后端与前端协作填数，不导出为 `.md` |
| 配置 JSON 导入导出 | 整机迁移用，不是报表正文 |
| `data/history/` 目录 | 启动时仍会创建；**不再**用于存放生成的 `.md` 报表（可为空或作它用） |

若未来业务 **明确要求**「可编辑的 `.md` 中间稿」或「Markdown 归档」，应单独立项评估，而不是恢复 2026-03 文档中的默认路径。
