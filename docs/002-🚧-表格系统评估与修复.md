# 002 · ReportEditor 表格系统评估与修复

> 2026-07-12 对 `_Prj/SD_SMA_ReportEditor/frontend/` 表格控件系统做的三路并行深度审计（几何度量层 / SQL 填充分页链路 / 组件层与重复），及据此规划的修复执行列表。
> 审计为静态代码求证（前端 node_modules 当时未装，未跑 vitest）；每条结论标 CONFIRMED（源码可判定）或 PLAUSIBLE（需运行验证）。
> 本机开发/测试：`npm install --prefix _Prj/SD_SMA_ReportEditor/frontend` 后 `npx vitest run <file>`（在 frontend 目录）。

## 系统范围

- **组件层**：`components/report-template/` — TemplateBodyCanvas.vue(2297)、TemplateElementProps.vue(1530)、LayoutPresetPaperCanvas.vue(1716)、ZoneTableStatic.vue(167)、TableColumnResizeGutters.vue(130)、TemplateTableSqlFillFields.vue(504)、TemplateTableSqlVisualPanel.vue(1650)
- **逻辑层**：`lib/report-template/` — model.ts(994)、layout-zone-element.ts(867)、table-cell-metrics.ts(369)、table-content-layout.ts(152)、table-sql-fill.ts(815)、table-sql-fill-preview.ts(529)、binding-preview-utils.ts(843)，及一批 table-sql-fill-*、scalar-sql-* 与约 20 个 `*.test.ts`

## 评级与总结

设计 B+ / 实现 B- / 完整度 C+。架构主干合理（预览=导出复用同一套 Vue 组件、异步竞态用 generation 兜住、底层度量数学正确），但存在三层系统性问题：(1) 预览取 1000 行/导出取全量造成分页份数「所见非所得」；(2) 表格模型复制成 Template 系与 Zone 系两套且已漂移；(3) 一批整类能力缺失（合并单元格、中间列增删、请求取消、跨份数据快照）。无致命崩溃 bug，但有多个导致数据错误或「打印与屏幕不一致」的正确性 bug。

# ⌛️ 未完成：P1-A 编辑器导出预览行数/份数与真实 PDF 对齐

- **问题（CONFIRMED）**：`table-sql-fill-preview.ts:267` `sqlFillQueryLimit` 在编辑器（`fullSqlFill=false`）取数上限 `min(maxRows,1000)`，仅真导出 `PdfExportView.vue:182` 传 `fullSqlFill:true` 取全量（默认 maxRows=2000，拆分场景 50000）。结果超过 1000 行时编辑器预览页数偏少；拆分场景 ≤1000 行被判「不拆、显示 1 份」，实际导出拆成 2+ 份。`splitReportCountForPreview` 系统性少报份数。
- **触发**：SQL 结果 >1000 行（默认阈值极易达到）。
- **修复方向**：预览取数上限与导出对齐；若为性能保留上限，须在预览显式提示「预览仅显示前 N 行 / 实际约 M 页 P 份」，不能静默少报。
- **验收**：`table-sql-fill-preview.test.ts` / `table-sql-fill-report-split.test.ts` 增补跨 1000 行的份数/页数用例，走 TDD。

# ⌛️ 未完成：P1-B 长内容 240px 静默裁剪 + 纵表 0 行渲染字面 "…"

- **240px 裁剪（CONFIRMED）**：`table-cell-metrics.ts:42` `estimateWrappedTextHeightPx` 用 `TABLE_CONTENT_ROW_HEIGHT_MAX_PX(=240)` 封顶，而 `model.ts:388` / `table-content-layout.ts:53` 调用时不传 maxRowHeightPx，恒用 240。窄列长文本 >240px 时行框只到 240、超出被裁、无溢出提示 → 内容丢失。
- **纵表 0 行 "…"（CONFIRMED 静态推演）**：`table-sql-fill-preview.ts:190` `formatVerticalSqlFillCell` 末尾 `return "…"`；`:303` 纵表 0 数据仍保留 `slotRows` 行；导出 refresh `silent:true` 使 `previewLoading=false` → 落到 "…"。纵向填充表筛选命中 0 条时 PDF 印出字面省略号。
- **修复方向**：内容感知行高按内容需要放开上限（或分行溢出而非裁剪）；纵表非 loading 且 0 数据时输出空串而非 "…"。
- **验收**：`table-cell-metrics.test.ts`、`table-sql-fill-preview.test.ts` 增补用例。

# ⌛️ 未完成：P2-A SQL 参数值前端拼接改真参数化（漏反斜杠转义）

- **问题（CONFIRMED）**：`binding-preview-utils.ts:473` `quoteSqlScalarValue` 仅 `'`→`''`，不转义反斜杠；`:568` `substituteScalarSqlParams` 把值字符串插值进 SQL 后 POST 给 `/database/query/sql`（`useReportBindingPreview.ts:414`），后端不再参数化。正常值 `C:\batch\` 即让字符串未终止、查询失败；恶意 OPC 值可断出字符串。表名侧有 `validateSqlIdentifier` 强校验（安全），参数值侧无等价防护。
- **关联**：这是后端 `database.py` 已修的 pk 过滤注入洞的「前端另一半」；根因同为客户端拼 SQL。
- **修复方向**：优先改为后端参数化（值走绑定参数下发）；若短期无法改协议，至少补方言正确转义（MySQL 同时转义 `\` 与 `'`）。需与后端协议一起定。
- **验收**：`binding-preview-utils` 相关 test 覆盖含反斜杠/引号的值；后端侧回归。

# ⌛️ 未完成：P2-B 窄/多列表格列宽拖拽失效

- **问题（CONFIRMED 推导）**：`table-cell-metrics.ts:341` `applyTableColumnResizeDeltaPx` 在内侧宽 < 列数×26 时钳制值符号反转，末行 `Math.max(lo, round(w))`（:368）把所有列强抬 26 破坏总宽守恒，下一帧被 `distributeTableColumnInnerWidthsPx` 归一化拉回近似均分。净效果：30 列表格在窄于 788px 的正文/页眉里列宽拖拽静默失效，做不出不等宽列。两画布因共用同一 clamp 公式同时中招。
- **修复方向**：拖拽数学在退化区（列宽已达下限）正确处理——不反转方向、不整体重置、保持总宽守恒；或在列宽和 < 下限总和时禁用拖拽并提示。
- **验收**：`report-template.test.ts` 增补窄内宽/多列退化区用例（现仅覆盖 inner=200/cols=3）。

# ⌛️ 未完成：P2-C 表格模型 Template 系 / Zone 系去重

- **问题（CONFIRMED）**：`model.ts`（Template*）与 `layout-zone-element.ts`（Zone*）约 11 对 1:1 平行复制（ensureTableGrid / intrinsicOuterHeight... / clampTableElementOuterSize 等）。**已漂移实证**：`intrinsicOuterHeightForZoneTable`（layout-zone-element.ts:536）对 SQL 填充有 `return chrome + rows*minH` 短路，`intrinsicOuterHeightForTemplateTable`（model.ts:368）无此短路 → 同一 SQL 填充表在正文与页眉页脚算出不同高度。
- **修复方向**：抽 `table-model-core`（cell/grid/度量/clamp 纯逻辑）让两系共享，仅保留各自 padding 常量差异；先对齐已漂移的 SQL 填充高度语义。属重构，改动面大，放在 P1 bug 修完后单独排期。
- **验收**：抽取后两系行为一致；现有 model/layout 相关 test 全绿 + 补漂移对齐用例。

# ⌛️ 未完成：P3 度量副作用 / 性能防抖 / 高缩放亚像素

- **度量函数带副作用（CONFIRMED）**：`templateTableColumnInnerWidthsPx`(model.ts:340)、`intrinsicOuterHeightForTemplateTable`(model.ts:368) 内部调 `ensureTableGrid` 就地改 `el.tableCells` 等；computed/渲染期调用产生非用户 mutation，undo/redo 隐患；一次 `clampTableElementOuterSize` 重复 ensure 约 5 次。
- **拖拽每步全表重算（PLAUSIBLE）**：`TemplateBodyCanvas.vue:1173` deep watch 每个 pointermove 触发全表 SQL 列目录重建 + 所有表 clamp，未防抖。
- **高缩放亚像素丢失（CONFIRMED 推导）**：`TableColumnResizeGutters.vue:72` 每次 move 推进 lastClientX 不留余数，`round` 归零则位移永久丢失；2.8× 缩放下细调列宽推不动。
- **修复方向**：度量函数拆纯只读版 / ensure 结果缓存；deep watch 防抖；拖拽累积亚像素余数。

# ⌛️ 未完成：盲区类能力缺口（需求确认后再定，非 bug 修复）

- 合并单元格（rowspan/colspan）完全不存在（全前端无 merge 字段）。
- 行列只能末尾增删：`ensureTableGrid` 末尾补/截，缩列永远丢最后一列，无法删中间列/重排。
- 拆分导出无统一数据快照：每份重新全量查询、各份取数时刻不同，DB 变动时跨份内容不一致；无 AbortController。
- 超页大行被 `overflow:hidden` 裁剪无跨页断行；最多 50000 行全量进 DOM 无虚拟化。
- 静态表跨页不重复表头（`includeHeaderRow:false` 硬编码）；时区不换算（只删 +00:00 后缀）；无千分位；布尔/二进制无专门格式化。
- 拖拽调宽/调尺寸键盘不可达（把手 tabindex=-1）。

## 亮点（保留，不动）

1. 预览=导出复用同一套 Vue 组件（PdfExportView → TemplateMiniPage），版式/切分/文案天然一致。
2. 异步竞态用 generation 自增 + await 边界校验兜住乱序覆盖。
3. 列宽拖拽把手 TableColumnResizeGutters 真·共用；底层度量数学两画布共享。
4. 撤销/重做 debounce 320ms 深拷贝快照，一次拖拽塌缩为一步。
5. 行高求和整数化无浮点漂移；列宽整数化用最大余数法保证和恒等。

## 执行顺序（据此推进）

1. **P1-B**（240px 裁剪 + 纵表 "…"）——纯逻辑层、影响客户可见输出、有现成 test，先做。
2. **P1-A**（预览/导出行数对齐）——同为「所见非所得」，逻辑层可 TDD。
3. **P2-A**（SQL 参数值转义/参数化）——安全 + 正确性，与后端协议一起定。
4. **P2-B**（窄表拖拽）——逻辑层可 TDD。
5. **P2-C 去重重构** 与 **P3 性能/副作用**——较大改动，前述稳定后单独排期。
6. **盲区能力**——需用户确认需求再立项。
