# ✅ 已完成：登记现象与代码对照根因（2026-07-20）

## 现象与现场证据

Windows 实际结批 CPU≈100%，同机 mappView 白屏/刷新。

| 证据 | 结果 |
|------|------|
| 并行上限与启用绑定数 | **均为 4** |
| 并行改为 1 | **白屏消失**；CPU 仍可 100% |
| 硬件 | **i3-7100U**；**DB 同机**；**Hypervisor 再少一核** |

根因：多路隐藏 Chromium + `printToPDF` 抢核（并行=1 已证实）；单路仍满负荷 + 分卷重复全量 SQL 拉长争用窗口。

# ✅ 已完成：分卷只取数一次 + 只渲染当前份（0.3.111）

| 项 | 做法 |
|----|------|
| 取数缓存 | `pdf-export-fill-cache.ts`：part0 `fullSqlFill` 后快照；part>0 复用，不再打全量 SQL；prewarm 清空 |
| 渲染 | `buildExportPreviewReports`：导出带 `reportPartIndex` 时只算该份 `computeExpandedBodyPreviewCards` |
| 接线 | `PdfExportView.boot`；`TemplateExportPreviewStack` |
| 单测 | cache U1–U3；reports U1；chrome U10–U11 |

**效果（相对 023）**：分卷场景累计 SQL 行数从约 `行数×份数` 降为约 **一行数（一次全量）**；每份不再重算其余 N−1 份 DOM 估高。

# 🚧 进行中：0.3.113 现场复核 — 分卷生成仍触发画面刷新（2026-07-21）

> **预期**：0.3.110/111（并行=1、BelowNormal、分卷 yield、fill-cache）应降低同机 HMI 争用，多分卷结批时不再「每生成一份就刷一次屏」。

## 现场现象（用户口述）

| 报表 | 数据规模 | 分卷 | 画面表现 |
|------|----------|------|----------|
| 配方报表 | （未量化） | — | **刷新 1 次** |
| 生产数据报表 | 约 **8000** 条 | **分 4 次**生成 | **每生成一份都触发一次画面刷新**（≈4 次） |

说明：此处「画面刷新」指同机 **mappView / HMI** 侧可见闪白或整页重绘，而非仅 Report Editor 自身预览重绘（若现场另有区分，后续补截图/录像）。

## 含义（相对已落地项）

- 并行=1 / 节制策略**未消除**「按分卷次数触发 HMI 刷新」；大表多分卷时刷新次数≈份数。  
- 与「长时间白屏消失」不矛盾：已从长白屏变为**短促多次刷新**，但在 **「完全不闪 / 掉线≈10s 重载」** 硬验收下 **仍算失败**。  
- 0.3.111 fill-cache 本条未测 `dataMs`；只登记 HMI 仍随份数闪。  
- **补充约束**：AR+Windows Hypervisor 下 mappView/Chromium **不可绑核** → 不能靠「互补亲和性」保 HMI。

# ✅ 已完成：导出「双模式」开关评估与命名（2026-07-21）

> **来源**：用户口述（「性能模式 / 质量模式」可改名；先评估记录，本条不改默认代码行为）。  
> **结论**：**值得做**；与策略 A「功能开关可回滚」一致，应做成面向现场的**导出模式**，而不是只暴露引擎技术名。

## 用户意图（转写）

| 口述名 | 期望行为 |
|--------|----------|
| 「性能模式」 | 用**更快 / 更省机**的路径生成 PDF |
| 「质量模式」 | 用**不闪 mappView** 的路径（同机 HMI 可操作） |
| （语音笔误疑似）「互相切换工具」 | 现场可一键在两种路径间切换 |

说明：口述里「质量 = 不闪」偏**产线可用性**，与日常说的「PDF 版式质量」容易撞名，故下面**弃用「性能/质量」作正式 UI 名**。

## 技术映射（两档够用）

当前只有两条可落地路径（第三档栅格/另一 Chromium 已否决）：

| 推荐正式名 | 内部引擎 | 行为 | 代价 |
|------------|----------|------|------|
| **同机优先**（默认，硬验收） | `pdf-lib` | **不**调用 `printToPDF`；取数/分卷仍可走隐藏窗，但跳过 DOM 打印尖峰 | 版式 **draft-v1**，与编辑预览非 1:1 |
| **版式优先**（回滚 / 对照） | `chromium` | 现网 `printToPDF`（DOM≈1:1） | 同机易抢核 → mappView **可能闪/卡**（0.3.113 已见） |

与口述对照：

- 「不闪」→ **同机优先**（正式默认）。  
- 「最快」→ 多数现场场景下也是 **同机优先**（少一轮 Chromium 排版/打印）；若指「PDF 看起来最像模版」则是 **版式优先**，墙钟不一定更短，但**版式保真更高**。

## 为何不用「性能 / 质量」

| 问题 | 说明 |
|------|------|
| 语义对撞 | 「质量」易被理解成 PDF 印刷/版式质量，实则用户指 HMI 不闪 |
| 「性能」歧义 | 可指墙钟、CPU、或 HMI 流畅度；三层不总同向 |
| 现场沟通 | 工控验收口语是「结批时 HMI 还能不能点」，用 **同机优先 / 版式优先** 更贴验收 |

可选副标题（设置页一行说明即可）：

- 同机优先：减轻结批对 mappView 争用；PDF 为草稿级版式。  
- 版式优先：PDF 接近编辑预览；同机可能闪屏（仅调试/无 HMI 同机时用）。

其它候选名（未采用）：轻载导出 / 高保真导出；稳运行 / 看版式。

## 产品规则（评估锁定，待实现）

1. **一档偏好，两处生效**：自动结批与手动导出共用同一模式（避免「手动好、自动炸」）。  
2. **默认 = 同机优先**（满足硬验收）；**版式优先**为显式回滚/对照。  
3. **设置入口**：报表生成 / 导出相关设置一处开关即可；高级可显示内部 `pdfExportEngine`。  
4. **审计必记**（便于现场口述难确认时给人看）：`exportMode`、`engine`、`printToPDFSkipped`、`layoutFidelity`、分卷数、`printMs`/`pdfLibMs`、`fontEmbedded`。  
5. **不引入第三档**（除非日后 pdf-lib 版式追上再考虑「自动」）。  
6. **与策略 A 一致**：先保零闪；版式在同机优先路径上渐进对齐，而不是靠切回 chromium 当长期默认。

## 风险与边界

- 同机优先初期 PDF **观感可能明显差于** 版式优先 → 交付说明与审计 `layoutFidelity=draft-v1` 必须写清。  
- 隐藏窗若仍做重 DOM 预览，同机优先收益会打折 → 实现时应在该模式下**跳过 TemplateExportPreviewStack / waitPaintReady**（只取数 + 矢量写 PDF）。  
- 现场若误开版式优先，会再现闪屏 → UI 需短警告文案。

# 🚧 进行中：同机优先 PDF 版式不可用（draft-v1 现场反馈 · 2026-07-22）

> **来源**：用户截图「SMA报警报表」同机模式导出。  
> **关联**：034 **M11**；原策略 A「先零闪、版式渐进」**已被下方产品拍板修正**。

## 现象（对照截图）

| 所见 | 代码含义 |
|------|----------|
| 版式变成自上而下纯文本，无表格框/坐标布局 | 当前 pdf-lib `layoutFidelity=draft-v1`（非预览 1:1） |
| `part … engine=pdf-lib · fidelity=draft-v1` 变成乱码碎片 | 嵌入字体/subset 异常或回退 Helvetica 后缺字 |
| 大量 `{{v}}` 原文 | pdf-lib 路径未做模版占位符插值 |
| `[table <uuid>]` 行 | 草稿路径表格标记，非预览表格 |

## 产品拍板（2026-07-22 · 用户）

| 项 | 决定 |
|----|------|
| 交付 PDF 观感 | **必须与预览一致**（编辑/导出预览所见即所得） |
| pdf-lib **draft-v1 草稿导出** | **不接受**作为交付路径；不得再以「草稿级可先用」交代现场 |
| 当前默认同机优先（pdf-lib） | **不满足**上述交付标准；须改引擎策略或把「同机」与「预览级 PDF」重新拆解 |
| 临时用法 | 需要正确版式时切 **版式优先**（chromium/`printToPDF`）；知悉同机可能抢核 |
