# ✅ 已完成：登记现象与代码对照根因（2026-07-20）

## 现象与现场证据

Windows 实际结批 CPU≈100%，同机 mappView 白屏/刷新。

| 证据 | 结果 |
|------|------|
| 并行上限与启用绑定数 | **均为 4** |
| 并行改为 1 | **白屏消失**；CPU 仍可 100% |
| 硬件 | **i3-7100U**；**DB 同机**；**Hypervisor 再少一核** |

根因：多路隐藏 Chromium + `printToPDF` 抢核（并行=1 已证实）；单路仍满负荷 + 分卷重复全量 SQL 拉长争用窗口。

# ✅ 已完成：分卷只取数一次 + 只渲染当前份（0.3.111）

| 项 | 做法 |
|----|------|
| 取数缓存 | `pdf-export-fill-cache.ts`：part0 `fullSqlFill` 后快照；part>0 复用，不再打全量 SQL；prewarm 清空 |
| 渲染 | `buildExportPreviewReports`：导出带 `reportPartIndex` 时只算该份 `computeExpandedBodyPreviewCards` |
| 接线 | `PdfExportView.boot`；`TemplateExportPreviewStack` |
| 单测 | cache U1–U3；reports U1；chrome U10–U11 |

**效果（相对 023）**：分卷场景累计 SQL 行数从约 `行数×份数` 降为约 **一行数（一次全量）**；每份不再重算其余 N−1 份 DOM 估高。

# 🚧 进行中：0.3.113 现场复核 — 分卷生成仍触发画面刷新（2026-07-21）

> **预期**：0.3.110/111（并行=1、BelowNormal、分卷 yield、fill-cache）应降低同机 HMI 争用，多分卷结批时不再「每生成一份就刷一次屏」。  
> **现状版本**：**0.3.113**（含 032 P1；导出写盘已 async）。

## 现场现象（用户口述）

| 报表 | 数据规模 | 分卷 | 画面表现 |
|------|----------|------|----------|
| 配方报表 | （未量化） | — | **刷新 1 次** |
| 生产数据报表 | 约 **8000** 条 | **分 4 次**生成 | **每生成一份都触发一次画面刷新**（≈4 次） |

说明：此处「画面刷新」指同机 **mappView / HMI** 侧可见闪白或整页重绘，而非仅 Report Editor 自身预览重绘（若现场另有区分，后续补截图/录像）。

## 含义（相对已落地项）

- 并行=1 / 节制策略**未消除**「按分卷次数触发 HMI 刷新」；大表多分卷时刷新次数≈份数。  
- 与「长时间白屏消失」不矛盾：已从长白屏变为**短促多次刷新**，但在 **「完全不闪 / 掉线≈10s 重载」** 硬验收下 **仍算失败**。  
- 0.3.111 fill-cache 本条未测 `dataMs`；只登记 HMI 仍随份数闪。  
- **补充约束**：AR+Windows Hypervisor 下 mappView/Chromium **不可绑核** → 不能靠「互补亲和性」保 HMI。

# ⌛️ 未完成：同机降负载架构（分机暂不可行 · 2026-07-21 拍板）

> **约束（用户 · 2026-07-21 补充）**  
> 1. **分机目前做不到** → 一律同机设计。  
> 2. **mappView 验收 = 完全不闪**：一旦闪掉/挂住，Chromium 重载约 **~10s**，产线不可接受。  
> 3. **Hypervisor = 贝加莱 AR + Windows 并存**：mappView 经 **Windows 侧 Chromium** 访问 AR；**无法给 mappView/浏览器设 CPU 相关性**。  
> 4. 因此「报表绑核 + HMI 互补绑核」**不成立**；最多只能限制 Report Editor 一侧。

## 约束下的现实判断

| 命题 | 结论 |
|------|------|
| 只绑报表、不绑 mappView，能否「确定」留核给 HMI？ | **不能确定**；调度器仍可能把 Chromium 与导出尖峰叠在同一核 |
| 0.3.110/111 静态节制 + 加长 yield，能否保证 **零闪**？ | **高度不确定**；最多把长白屏变成短闪，**与「完全不闪」目标冲突风险大** |
| 同机 + `printToPDF`（Chromium）+ 另一 Chromium（mappView） | 两路浏览器内核争 CPU/GPU；这是结构冲突，不是调参能根治 |
| 要逼近「完全不闪」同机还能靠什么？ | 见下表 **零闪向** 选项；P0 错峰 alone **不应再承诺零闪** |

## 同机且目标「完全不闪」时的选项（按可行性）

| 优先级 | 方向 | 能否服务「完全不闪」 | 说明 |
|--------|------|----------------------|------|
| **Z1** | **结批/导出与 HMI 互斥时段** | 最接近 | 导出前操作员确认 / 自动仅在无操作窗口跑；导出中明确「HMI 可能不可用」则与「完全不闪」矛盾——若必须一直可操作，则 Z1 不够 |
| **Z2** | **旁路 `printToPDF`**（轻量/服务端/非 Chromium 出 PDF） | 高潜力 | 去掉「第二套 Chromium 打满」；工程量大，但是同机零闪的主技术候选（032 P2-B） |
| **Z3** | 导出极慢切片 + Idle 优先级 + 仅 1 逻辑核亲和（仅报表） | 中低 | 降低尖峰概率，**不保证**零闪；结批墙钟显著变长 |
| **Z4** | 结批时停一切非必要 Windows 负载（轮询/缩略图/探活） | 辅助 | 减背景争用，挡不住单次 print 尖峰 |
| ~~绑核双边~~ | ~~报表与 mappView 互补亲和性~~ | **不可用** | mappView/Chromium 不可设相关性 |
| ~~分机~~ | ~~报表机隔离~~ | **近期不可用** | 现场约束 |

## 对既有「同机 P0–P4」的修正

原 P0（错峰/让路）在 **「允许短闪」** 假设下有意义；在 **「完全不闪」** 下：

- **不得再把 P0 写成验收「HMI 零闪」的主路径**。  
- P0/Z3 仅作 **降低掉线概率的缓解**，须用现场录像验收「是否仍闪」。  
- 若现场仍闪一次即失败 → 必须评估 **Z2 换引擎** 或接受 **Z1 互斥导出**（导出窗口内不要求操作 HMI）。

## 推荐优先级（同机 · 零闪目标）

| 优先级 | 方向 | 做什么 | 预期对 HMI |
|--------|------|--------|------------|
| **先拍板** | 导出时 HMI 是否允许不可操作 | Z1：互斥 / 维护窗结批 | 互斥则可零闪；在线操作则不能靠互斥 |
| **P0′** | 缓解（不承诺零闪） | 更长 yield、Idle、报表单侧绑 1 核、降 B 级 | 降掉线概率；须实测 |
| **P1′** | **换/旁路 printToPDF** | 非第二 Chromium 或迁出重渲染 | 同机零闪主技术路径 |
| **P2′** | 导出 Job 化 | 可控排队、可取消、可限流 | 配合 P0′/P1′ |
| — | ~~互补绑核 / 分机~~ | — | **不可用** |
